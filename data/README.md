# Data dictionary: `nium-dashboard-mock-data.json`

**Everything in this file is synthetic.** It is demo data for a design prototype. It is not real Nium traffic, real customer data, or measured Nium performance. Customer names (Acme, Airbnb, Initech) are illustrative placeholders, each suffixed "(demo)".

- Generated by `scripts/generate-mock-data.mjs` (seeded, deterministic). Regenerate with `npm run data:generate`.
- Validated by `scripts/validate-data.mjs` (`npm run data:validate`).
- The app imports this exact file through `src/data/repository.ts`. The in-app **Download mock data (JSON)** button serialises that same imported object.
- **Two layers, like a real observability stack (schema 2.0):**
  - `metrics`: every simulated request (about 85,000 over 24 h) is counted in 5-minute aggregates per customer, environment and endpoint, with a latency histogram. KPIs, charts, service health and percentiles (P50/P90/P95/P99) come from here, computed in `src/data/selectors.ts`.
  - `requests`: the retained request log behind the activity table and triage. It keeps **every** failed and slow (≥1 s) request, payouts that later failed or had webhook problems, and a **1% sample** of other successful requests.
  - `webhookMetrics` / `webhooks`: the same split for webhook deliveries.
- `npm run data:validate` proves the layers agree: every failure and slow request counted in the metrics exists in the retained log, histograms sum to totals, and percentile order holds for every scope.
- "Now" for the dataset is `meta.anchorTime` (2026-10-17T12:00:00Z). Time ranges (1h / 6h / 24h) are measured back from this anchor.

## Official vs dashboard-specific fields

| Marker | Meaning |
| --- | --- |
| **Official** | Name or concept documented in Nium's public developer docs |
| **Dashboard** | Invented for this prototype's monitoring model |

`docStatus` on each endpoint records how confident we are in the path:
`verified` (seen in public docs during research), `unverified` (follows the documented `/api/v1/client/{clientHashId}/customer/{customerHashId}/wallet/{walletHashId}` pattern but the exact path was not confirmed), `illustrative` (placeholder; not a claimed Nium endpoint).

> Research note: docs.nium.com was not reachable from the build environment, so verification relied on search-indexed excerpts of the public docs. Re-check every `unverified` and `illustrative` item against the live docs before reuse.

## Top level

| Key | Type | Description |
| --- | --- | --- |
| `meta` | object | Name, schema version, anchor time, disclaimer, research sources, documented facts used |
| `services` | Service[] | Payments, Payouts, FX, Wallets with P95 latency targets (Dashboard) |
| `endpoints` | Endpoint[] | Endpoint catalogue with `docStatus` |
| `customers` | Customer[] | Demo tenants, provisioned environments, webhook host, brand accent |
| `telemetrySources` | TelemetrySource[] | Per customer × environment × service: `live`, `stale` or `missing` |
| `metrics` | object | `series[]` per customer/environment/endpoint; each point is `[bucket, total, clientErrors, serverErrors, timeouts, slow, asyncPayoutFailures, ...histogram]`; bins in `latencyBinsMs` (last bin = 30 s timeouts) |
| `webhookMetrics` | object | `series[]` per customer/environment; points `[bucket, total, delivered, delayed, failed]` |
| `requests` | ApiRequest[] | Retained request log (see retention rules) |
| `webhooks` | WebhookDelivery[] | Retained webhook log: all failed and delayed deliveries plus a 1% sample |
| `alerts` | AlertConfig[] | Seed alert configurations (notifications are simulated) |

## `requests[]`

| Field | Type | Source | Notes |
| --- | --- | --- | --- |
| `requestId` | string | Dashboard | Stable id, `req_demo_00001` |
| `xRequestId` | uuid | Official concept | Nium requires a 36-char UUID in the `x-request-id` header on every request |
| `traceId` | string | Dashboard | `demo-trace-xxxxxxxx`; stands in for a tracing-backend id |
| `customerId` | string | Dashboard | FK to `customers[].id` |
| `environment` | `sandbox` \| `production` | Official concept | Sandbox and Production records never share ids |
| `service` | `payments` \| `payouts` \| `fx` \| `wallets` | Dashboard grouping | |
| `endpointId`, `method`, `endpoint` | string | See `docStatus` | Path template, no real hash ids |
| `timestamp` | ISO-8601 UTC | Dashboard | Within 24h before `meta.anchorTime` |
| `httpStatus` | number | Standard HTTP | 200/201 success; 400/401/403/409/422/429 client; 500/502/503 server; 504 timeout |
| `latencyMs` | number | Dashboard | Lognormal per endpoint; timeouts recorded as 30000 |
| `outcome` | `success` \| `client_error` \| `server_error` \| `timeout` | Dashboard | Always consistent with `httpStatus` |
| `errorCode`, `errorSummary` | string \| null | Dashboard | Prototype vocabulary, **not** official Nium error codes. Null only on success |
| `traceAvailable` | boolean | Dashboard | False simulates traces not retained (edge case) |
| `region` | string | Dashboard | Internal-only; hidden in customer view |
| `systemReferenceNumber` | string \| null | Official field name | Present on accepted Transfer money calls |
| `transactionStatus` | `INITIATED` \| `PAID` \| `FAILED` \| `RETURNED` \| null | Dashboard model | Async payout outcome, aligned to webhook templates |
| `incident` | string \| null | Dashboard | Label of the synthetic incident that shaped this record |
| `retention` | `error` \| `slow` \| `payout_failed` \| `webhook_issue` \| `sampled` | Dashboard | Why this request was kept in the log |
| `synthetic` | `true` | Dashboard | Always true |

## `webhooks[]`

| Field | Notes |
| --- | --- |
| `template` | `REMIT_TRANSACTION_INITIATED_WEBHOOK` and `REMIT_TRANSACTION_PAID_WEBHOOK` are documented. `..._FAILED_WEBHOOK` and `..._RETURNED_WEBHOOK` follow the same naming but were **not verified** |
| `relatedRequestId` | FK to the Transfer money request that caused it |
| `deliveryStatus` | `delivered`, `delayed` (succeeded after retries, > 45 s) or `failed` (5 attempts exhausted) |
| `attempts`, `responseStatus`, `deliveryLatencyMs` | Customer endpoint behaviour (Dashboard). Retry counts are illustrative, not Nium's documented retry policy |
| `customerEndpointHost` | `*.example` hosts only |

## `telemetrySources[]`

`status` drives the Unknown state. `missing` means no records exist for that service. `stale` means the newest record is older than 3 hours. **Neither is ever shown as healthy.**

## Documented facts used

- Sandbox usage limits: 50 requests/second, burst 50/second, 25,000 requests/day. Production limits are not published, so the dataset only models 429s in Sandbox.
- `x-request-id` (UUID) and `x-client-name` headers are required on requests. `x-api-key` is never stored; the UI shows it as "Redacted".

## Built-in scenarios

| Customer · Env | Scenario |
| --- | --- |
| Acme · Production | ~32,000 requests/day. FX latency degradation 3.5 h to 1.5 h ago; webhook delivery just under 97% |
| Acme · Sandbox | ~3,700 requests/day. Onboarding noise: validation and auth errors, a 60-request 429 burst |
| Airbnb · Production | ~48,000 requests/day (~3,800 in the last 90 min). Payout partner errors over the last 45 min (502/500/504 cluster, ~7.7% of payout calls) |
| Airbnb · Sandbox | ~950 requests/day. Wallets telemetry missing, Payments telemetry stale |
| Initech · Sandbox | No traffic yet (empty state). Production not provisioned |

## Assumptions

Latency targets (P95: Payments/Payouts 600 ms, FX 500 ms, Wallets 400 ms), P50 around 150–220 ms, occasional > 1 s outliers and the health thresholds in `src/data/selectors.ts` are illustrative starting points, **not Nium SLAs or measurements**.
